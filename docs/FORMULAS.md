# Формулы и единицы FlowLens (`flowlens-1.0`)

Это спецификация **нашей** реализации. Формулы не восстановлены из закрытых
алгоритмов референсных терминалов и не претендуют на совпадение с ними.
Версия алгоритма (`algorithm`), параметры (`params`) и их хэш (`params_hash`)
возвращаются в каждом ответе `/api/chart` и `/api/indicators`.

## Обозначения

| Символ | Смысл | Единица |
|---|---|---|
| `p` | цена уровня | котируемая валюта (USDT) |
| `q` | количество на уровне / в сделке | базовый актив (BTC) |
| `N = p × q` | номинал | котируемая валюта |
| `mid` | `(bestBid + bestAsk) / 2` | цена |
| `r` | относительная глубина: 0.0025, 0.005, 0.01 (+0.03, 0.05, 0.10) | доля |
| `B_r` | Σ `p×q` бидов с ценой в `[mid×(1−r), mid]` | номинал |
| `A_r` | Σ `p×q` асков с ценой в `[mid, mid×(1+r)]` | номинал |

Режим единиц (`params.units`): `quote` — суммы в номинале, `base` — в
количестве базового актива. BTC и USDT никогда не складываются в одной серии.
Каждый ответ API содержит блок `units`.

Цены и количества в стакане и в суммах объёмов хранятся целыми числами с
масштабом 1e8 (`numeric.py`). Плавающая точка используется только для
номиналов в выдаче и для статистики.

## Стакан

### Покрытие глубины (`coverage`, `valid`)

REST-снимок отдаёт не более N уровней на сторону (Binance Spot 5000,
USD-M 1000), Bybit-поток держит top-N (spot 200, linear 500). Уровни глубже
снимка неизвестны, пока не изменятся. Поэтому для каждой стороны хранится
нижняя граница известного диапазона (`bid_floor`/`ask_ceil` для Binance,
самый глубокий удерживаемый уровень для top-N).

* `coverage_r = min(1, (mid − bid_floor) / (mid × r))` (для асков симметрично).
* Отсчёт полосы `r` считается валидным, только если `coverage_r = 1`.
* Минута стакана валидна по полосе, если полностью покрытые отсчёты составляют
  ≥ 90 % её времени. Иначе значение `null`, а не 0; покрытие отдаётся рядом.
* У Binance Spot снимок 5000 уровней может не дотягиваться до 1 %: раз в
  5 минут (не чаще) коллектор берёт свежий снимок и подменяет книгу **без
  разрыва** последовательности: новый снимок догоняется событиями из
  кольцевого буфера уже применённых обновлений и включается, когда его
  `update id` совпадает с текущим.

### Отсчёты и агрегирование

* Каждую секунду (UTC-сетка, `sample_ms`) берётся отсчёт книги: `mid`,
  спред, `B_r`/`A_r` (накопительно) для всех `r`, бакеты карты глубины.
* Минутный кадр — средневзвешенное по времени (вес = время отсчёта, мс) по
  валидным отсчётам. Хранится `time_ms` — покрытое время.
* Свеча таймфрейма `tf` = средневзвешенное минутных кадров. Значение свечи
  выдаётся, если покрытое время ≥ `book_min_time_cov × tf` (по умолчанию 0.5),
  и с долей покрытия `time_cov` в подсказке.
* Время стакана — время получения (local receive), рядом хранится медианная
  задержка «получение − время биржи» (`lag_ms`). Свечи и футпринт привязаны ко
  времени сделки на бирже.

### Дельта стакана

`OrderbookDelta_r = B_r − A_r`. Панель показывает `B_r` (зелёная), `A_r`
(красная) и разницу (синяя) или гистограмму разницы. Это дисбаланс **стоящих
заявок**, а не дельта сделок и не изменение стакана за интервал.

### Bid Dominance

* Основной режим: `Imbalance_r = 100 × (B_r − A_r) / (B_r + A_r)`,
  диапазон −100…100, ноль — баланс.
* Режим `bid_share`: `BidShare_r = 100 × B_r / (B_r + A_r)`, диапазон
  0…100, баланс 50.
* Три линии: 0.25 % (жёлтая), 0.5 % (серая), 1 % (синяя пунктирная).
* `B_r + A_r = 0` или отсутствие любого из слагаемых → `null`.
* Для свечи сначала усредняются `B_r` и `A_r`, затем считается отношение.

Проверка: `B = 150, A = 100 → Delta = 50, Imbalance = 20 %, BidShare = 60 %`.

### Imbalance Dynamics

`Dynamics_r(t) = Imbalance_r(t) − Imbalance_r(t − Δt)` в процентных пунктах.
`Δt` — число свечей (`dyn_lag`, по умолчанию 1). Пропуск любого из значений →
`null`. Опционально EMA (`dyn_ema` > 1, `α = 2/(n+1)`); пропуск входа
перезапускает EMA. Проверка: −10 % → 20 % даёт 30 п.п.

### Полосы дисбаланса (облака под ценой)

Предложенная логика нашей версии. Вокруг исторического `mid` три
**непересекающихся** пояса: 0–0.25 %, 0.25–0.5 %, 0.5–1 %. Объём пояса —
разность накопительных сумм (`B_0.5 − B_0.25` и т. д.), отдельно для бидов
(ниже цены) и асков (выше).

Цвет пояса — по z-score объёма этой стороны и пояса (см. ниже):

| Условие | Цвет |
|---|---|
| `z ≥ +порог` | насыщенный зелёный (биды) / красный (аски) — «выше базы» |
| `−порог < z < +порог` | зелёный / красный, прозрачность растёт с z |
| `z ≤ −порог` | оранжевый (биды) / голубой (аски) — «ниже базы» |
| прогрев, σ = 0 | нейтральная серая заливка |

Подписи легенды — «ниже/выше базы», а не «снятие заявок» или «крупный игрок».
Порог, база, палитра, прозрачность настраиваются. Алгоритм цвета изолирован в
`beltColor()` (frontend) и `compute_indicators()` → `belts` (backend).

### Карта глубины

Ось X — время, Y — абсолютная цена. Ячейка — объём лимитных заявок в ценовом
бакете (`heatmap_step`, для BTC по умолчанию 10 USDT) в диапазоне ±3 % от
`mid`. Минутная ячейка хранит и средневзвешенное по времени, и максимум;
при укрупнении по времени пользователь выбирает «среднее» или «максимум».
Ячейки вне покрытого диапазона стакана — `NaN` (прозрачные), не ноль; пропуски
последним значением не заполняются. В режиме «номинал» значение ≈ количество ×
середина бакета (погрешность ≤ шаг/2/цена). Это текущие заявки на каждом шаге
истории, а не сумма за период, и не карта ликвидаций.

## Сделки

### Объём и дельта

Сторона агрессора — по семантике API:

* Binance `aggTrade`: `m = true` (покупатель — мейкер) → агрессор продаёт;
  `m = false` → покупает. Одна запись агрегирует исполнения одной тейкер-заявки
  по одной цене; число исполнений = `l − f + 1`.
* Bybit `publicTrade`: `S = Buy/Sell` — сторона тейкера; одна запись = одна
  сделка.

`Delta = Vbuy − Vsell`, `total = Vbuy + Vsell` в одинаковых единицах.
Сделки без стороны учитываются отдельно (`v_unknown`, `n_unknown`).
Проверка: `Vbuy = 12, Vsell = 8 → Delta = 4, total = 20`.

Дельта количества сделок `Nbuy − Nsell` считается по исполнениям. Для истории,
загруженной из свечей биржи, разбивки по стороне нет → `null`
(«нет разбивки»). У Bybit в свечах нет и объёма тейкер-покупок, поэтому для
истории Bybit до запуска дельта объёма тоже `null`.

### Непрерывность потока сделок

У Binance id агрегированных сделок идут подряд. Разрыв id → дозагрузка
пропуска по REST `aggTrades?fromId=` и пометка свечи; дубликаты отбрасываются.
Минута, начавшаяся до подключения, помечается неполной и после закрытия
заменяется свечой биржи (`kline_reconciled`), футпринт остаётся помеченным
как частичный. У Bybit id — строки, непрерывность проверить нельзя, полнота
определяется непрерывностью соединения.

### CVD

`CVD = Σ Delta` с моментом сброса: UTC-день (по умолчанию), ежедневная сессия
с началом `cvd_session_start` минут после 00:00 UTC, либо начало загруженной
истории. Точка после пропуска или неполной свечи помечается `cvd_partial`.

### Аномальный поток сделок (альтернатива BGW)

Для каждой стороны: `x` — объём агрессора за свечу; база — `window` (100)
предыдущих **завершённых** свечей без пропусков:
`ratio = x / mean`, `z = (x − mean) / std` (популяционное std).
Свечи с `ratio ≥ threshold` (×3) объединяются в эпизод; подпись ставится у
максимума: сумма эпизода, сторона, множитель. Пока валидных свечей меньше 90 %
окна — «прогрев». Порог и окно — проектные значения, не параметры BGW.

## Z-score

На фиксированной временной сетке таймфрейма:
`z(t) = (x(t) − mean_prev) / std_prev`, где база — слоты
`[t − W, t − 1]` (W = база / tf), текущий отсчёт и будущее в базу не входят,
`std` популяционное. Требования: ≥ 30 валидных отсчётов и ≥ 90 % покрытия
окна, иначе статус `warmup`; нулевая дисперсия → `zero_var`; нет значения →
`nodata`. База выбирается временем (1h…14d), а не числом сообщений. Порог по
умолчанию |z| ≥ 3.

## Футпринт и профиль

* Футпринт: реальные сделки по свече и ценовому бакету: покупки, продажи,
  total, дельта, число сделок, дельта числа сделок. Хранится с базовым шагом
  (для BTC 5 USDT); детализация 10/20/50 или свой шаг, кратный базовому
  (а он кратен tick size).
* Профиль: сумма исполнений по цене за видимый период. Не строится из стоящих
  заявок.
* POC — бакет с максимальным объёмом (при равенстве — с меньшей ценой).
  Value Area 70 %: от POC добавляется больший из соседей сверху/снизу; при
  равенстве добавляются оба; остановка при ≥ 70 % объёма.

## Классика

* RSI: Уайлдер, период 14, уровни 30/70, на закрытиях свечей; формирующаяся
  свеча считается отдельно (`rsi.live`).
* MACD: EMA 12/26, сигнальная EMA 9; значение появляется после прогрева
  медленной EMA.

## Деривативы

* OI: Binance — REST `openInterest` каждые 30 с и история `openInterestHist`
  (5 мин); Bybit — поток `tickers` и история `open-interest` (5 мин).
  Изменение OI — разница соседних свечей.
* Funding: ставка за период (Binance `markPrice@1s` и `fundingRate`, Bybit
  `tickers`), время следующего начисления и длина периода.
* Ликвидации: Binance `forceOrder` (сторона ордера SELL = ликвидирован лонг;
  поток отдаёт не более одной ликвидации в секунду на символ — **неполный**),
  Bybit `liquidation` (side `Buy` = ликвидирован лонг, по документации).
* На споте — «Неприменимо».
